# Tasks: phase16_rmcp-server-migration

Migrate `nexus-server` off the vulnerable rmcp 0.8.3 (RUSTSEC-2026-0189) to 2.2.0.
Section 1 comes first deliberately: the `/mcp` transport layer this migration breaks
is currently the one layer with no compiled test coverage, so migrating first would
ship unvalidated. Does not close issue #28 — phase15 does that independently.

## 3. Validate the migration
- [x] 3.1 Re-ran the section 1 suites on rmcp 2.2.0: 19 unit tests + the transport handshake test PASS. The transport test caught a REAL behavior change (below), which is exactly why the baseline came first — compile success alone would have missed it
- [x] 3.2 Transport handshake (initialize → notifications/initialized → tools/list → tools/call) verified green through the real `StreamableHttpService`. TWO client-visible changes found, both to be called out in release notes (4.1): (a) rmcp ≥1.x enforces **DNS-rebinding protection** — `/mcp` now requires a `Host` header in an allowed list (default localhost/127.0.0.1/::1), so 0.0.0.0 deployments accessed via hostname/IP get 403; per user decision we KEEP the secure default and expose a config knob as a follow-up (see phase19). (b) advertised `ProtocolVersion` default moved `2025-03-26` → `2025-11-25` (rmcp negotiates with the client, so practical impact is low — 2024-11-05 is still in `KNOWN_VERSIONS`)
- [x] 3.3 `cargo audit` clean for this advisory: RUSTSEC-2026-0189 no longer reported, rmcp is no longer a flagged vulnerable crate, and only rmcp 2.2.0 (no 0.8.x) remains in `Cargo.lock`. (Unrelated pre-existing advisories in `bytes`/`rustls-webpki`/`rsa`/etc. are out of scope for this rmcp task)
