## 1. Implementation
- [x] 1.1 Parse a pattern as a predicate wherever a boolean expression is legal
      — Confirmed on a live server before editing, and the proposal's framing is right for
      once: `NOT (n)-[:T]->()` and `exists { (n)-[:T]->() }` both worked, so the evaluation
      machinery was already wired and only the grammar entry point was missing. One case
      the proposal does not list also failed: the projection form,
      `RETURN (n)-[:T]->() AS has`.
      That extra case decided the design. Rather than special-casing `WHERE`, the pattern
      attempt goes in at the **primary-expression** level
      (`parser/expressions/primary.rs`), which makes the bare form, either side of an
      `AND`/`OR`/`XOR`, and the projection form all work with no per-form code. Every form
      produces the same `Expression::Exists { inner: ExistsInner::Pattern { .. } }` the
      `NOT` form already produced, so nothing downstream changed.
      `try_parse_not_pattern` was renamed `try_parse_pattern_predicate` — it now serves
      positive forms and the `not_` in the name would have been a lie.
- [x] 1.2 Route all forms to the evaluation path the `NOT` form already uses
      — Including the function-style `exists(<pattern>)`, wired in
      `parser/expressions/identifier.rs` following the `shortestPath`/`allShortestPaths`
      precedent already in that file. `exists(n.prop)` and `exists { … }` are untouched.
- [x] 1.3 Composition with AND/OR/XOR — falls out of the primary-level placement; verified
      on both sides of an `AND`.

Per-scenario, the with-orderBy failures that move are `[15] Sort by an aliased aggregate
projection does allow subsequent matching` and `[23] Sort by an expression that is only
partially orderable …` — `[23]` is the coin flip isolated during
`phase22_tck-aggregation-grouping-key`, and `[15]` is a second one in the same family:
its query ends `ORDER BY rel.id`, sorting by a *property of a projected alias*, which is
the same "ORDER BY over a key that is not itself a projected column" path. The
`clauses/return` mover is the map-key-order scenario isolated during
`phase22_tck-temporal-subsecond-components`. None of the three is reachable from this
task's diff, which touches only the expression parser.

Note for the next measurement: the earlier finding that "two identical runs produce
byte-identical reports" does NOT generalise — it held for one build and misled me into
treating a −1 as necessarily real. Determinism must be re-established per build, not
assumed.

Before → after, measured on a live server with
`CREATE (:A {n:1})-[:T]->(:B {n:2}), (:A {n:3})`:

| Query | Before | After |
|---|---|---|
| `WHERE (n)-[:T]->()` | parse error at the `-` | `[[1]]` |
| `WHERE exists((n)-[:T]->())` | parse error | `[[1]]` |
| `WHERE (n)-[:T]->() AND n.n = 1` | parse error | `[[1]]` |
| `WHERE n.n = 1 AND (n)-[:T]->()` | parse error | `[[1]]` |
| `RETURN n.n, (n)-[:T]->() AS has` | parse error | `[[1, true], [3, false]]` |
| `WHERE NOT (n)-[:T]->()` | `[[3]]` | `[[3]]` unchanged |
| `WHERE exists { (n)-[:T]->() }` | `[[1]]` | `[[1]]` unchanged |
| `WHERE (n.n) = 1` | `[[1]]` | `[[1]]` unchanged |
| `RETURN (1 + 2) = 3` | `true` | `true` unchanged |

The disambiguation is what makes this safe, and it was already in the code being
reused: the pattern attempt requires a `-` or `<` after the first node, so a
parenthesized expression can never be swallowed. Both no-change rows above are
regression-tested, not just observed.
