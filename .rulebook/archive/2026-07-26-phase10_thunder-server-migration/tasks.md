## 4. Dissolve nexus-protocol::rpc — consumers use thunder-rpc directly (crate is deleted in phase11)
**USER DECISION (2026-07-25): do NOT keep a nexus-protocol::rpc shim.** The user does not want `nexus-protocol` as the shared publishable crate for the RPC wire — each side normalizes on `thunder-rpc` directly (registry crate). So instead of a re-export shim, the `rpc` module was DELETED and every consumer now depends on `thunder-rpc` directly. Key win: **the Rust SDK no longer depends on `nexus-protocol` at all** (it depended on nothing but `nexus_protocol::rpc`), so `nexus-graph-sdk` now depends only on published crates.
- [x] 4.1 ~~Replace types.rs + codec.rs with re-exports~~ → **DELETED `crates/nexus-protocol/src/rpc/` entirely** (types.rs + codec.rs + mod.rs) and removed `pub mod rpc;` from `lib.rs`. All consumers migrated to `thunder::{Value as NexusValue, Request, Response}`, `thunder::wire::{encode_frame, decode_frame, read_response, write_request, …}`, `thunder::PUSH_ID`. The ONE API adaptation: Thunder's async `read_*`/`write_*` additionally return the frame size (`(T, usize)` / `usize`), so read sites destructure `let (resp, _) = read_response(..)` (or a 3-line local wrapper in the two integration tests) and write sites drop the returned `usize`. Thunder's `Bytes` is `Arc<[u8]>`: 2 consumer read sites fixed (nexus-cli `b.iter().copied()`, nexus-bench `from_utf8(b.to_vec())`).
- [x] 4.2 ~~Add thunder-rpc to nexus-protocol~~ → **removed the RPC concern from `nexus-protocol` entirely** (no thunder dep there; `rmp-serde` dropped — it was only used by the deleted codec). Added `thunder-rpc = { …, features = ["tokio"] }` to the CONSUMERS instead: `nexus-cli`, `nexus-bench` (optional, in `live-bench`), `nexus-core` (dev-dep, for the `protocol_point_read` bench), and `sdks/rust` (explicit registry version — it's a standalone crate, not a workspace member, so it can't inherit `workspace = true`). Each consumer that ONLY used `nexus_protocol::rpc` dropped the `nexus-protocol` dependency (nexus-cli, sdks/rust, nexus-bench, nexus-core). `rest.rs`/`mcp.rs`/`umicp.rs`/`resp3/` untouched — still used by `nexus-server` (an mcp integration test), so `nexus-protocol` remains a workspace crate for those (their own dissolution is a separate follow-up).
